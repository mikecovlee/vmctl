# v1.0 release goals

vmctl 1.0 is a reliable single-host CLI for installing and operating Linux and
Windows guests on Linux x86-64 with Docker, QEMU and KVM. Release readiness means
installation from an empty disk, predictable lifecycle operations, recoverable
persistent data and actionable diagnostics.

This is the release acceptance checklist. A checked item requires recorded
evidence; an implementation alone does not complete its operational acceptance.
Current guest evidence is in [validation](validation.md).

## Installation and configuration

- [x] Strict `v1alpha1` configuration and relative media path resolution.
- [x] ISO examples for Kylin, Ubuntu, Windows 11 and Windows Server.
- [x] Kickstart, Ubuntu autoinstall and Windows unattended preparation.
- [ ] Install every final example from an empty disk on the release candidate;
  record ISO SHA-256, runtime image ID, guest version, login, shutdown and restart.
- [ ] Resolve Windows OpenSSH Preview packaging before calling its default
  installation suitable for production; record the supported replacement.

## Lifecycle and recovery

- [x] Create, install, finish-install, start, stop, pause, resume and delete.
- [x] Per-instance locking and ownership checks before container operations.
- [x] Explicit forced power-off; normal shutdown timeout leaves the VM running.
- [ ] Test recovery after host reboot, Docker restart and abnormal QEMU exit.
  Existing instances must remain discoverable and startable with preserved identity.
- [ ] Test interrupted creation, installation, import, snapshot and restore;
  document retry or recovery for every persistent intermediate state.
- [ ] Test full filesystems and permission failures, preserving the original
  instance or a usable recovery copy and returning a nonzero result.

Containers retain the explicit-start policy: recovery does not imply automatic
guest restart. Installation phase and current runtime status remain separate.

## Persistent data and compatibility

- [x] Stopped snapshots and export/import of disk, installation record and
  applicable NVRAM/TPM identity.
- [x] Import validates paths, payload checksums and self-contained qcow2 disks.
- [ ] Restore a release-candidate backup in a clean state directory; verify
  guest files, SSH identity and applicable UEFI/TPM identity.
- [ ] Exercise cancellation, corruption and space exhaustion against backups.
- [ ] Record supported CLI/bundle/config/runtime version combinations and an
  upgrade/rollback drill without replacing instance identities.

External SSH keys and installation media must be backed up separately as described
in [lifecycle](lifecycle.md#stopped-export-and-import).

## Networking and access

- [x] Isolated and outbound user networking, explicit TCP forwards and localhost
  management defaults.
- [x] Input validation and startup port-conflict checks.
- [ ] Release-candidate real-guest tests for isolation, outbound TCP/UDP, inbound
  TCP and stopped network updates, using proven controlled endpoints.

## Operations and distribution

- [x] Versioned CLI artifacts with build identity and SHA-256 checksums.
- [ ] Record the runtime image ID/digest and installed QEMU, firmware and TPM
  package versions for each release; publish matching build instructions.
- [x] Document clean-host setup, restart recovery, backup restoration, upgrades,
  resource capacity and monitoring of guest processes and free disk space; see
  [operations](operations.md) and the root quick start.
- [ ] Exercise diagnostics for unavailable Docker/KVM, missing media, invalid
  permissions, occupied ports and full storage.

## Release qualification

- [x] CI race/shuffle tests, vet, build, shell/config/docs and archive checks.
- [x] Repeatable opt-in KVM regression procedure with disposable instances;
  see [release qualification](release-validation.md). Execution remains required
  by the guest and recovery gates above.
- [ ] Record at least 14 consecutive days of representative guest operation,
  including repeated lifecycle operations and a backup recovery drill.
- [ ] No unresolved corruption, unintended deletion, identity-loss or blocked
  recovery defects. Record remaining nonblocking issues in release notes.

Never set the release version to `v1.0.0` until these acceptance gates pass.
Candidate artifacts use `v1.0.0-rc.N`.

## Experimental memory checkpoint

BIOS guests without TPM retain experimental memory checkpoint support. Ubuntu
and Windows Server RAM restoration have real-guest evidence. Document the exact
runtime/CPU/machine requirements and unknown outcome after timeout. This feature
does not block 1.0's stable lifecycle and persistent-backup capabilities.

## Scope

The stable target is a local single-host CLI. Multi-tenancy, a web console,
cluster scheduling, live migration, high availability and Windows hosts belong
to later versions.
